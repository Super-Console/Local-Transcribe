# VoiceToTextApp 开发任务书（工作版）

> 项目工作名：`VoiceToTextApp`（仅占位；产品名未决定）  
> 依据：`GPT聊天记录/本地转写软件方案.md` 中 Timmy 的明确选择与约束。  
> 状态：需求已整理；UI 和若干工程选型未定；不是最终视觉稿，也不代表下述候选技术已通过实测。

## 1. 产品目标

开发一个轻量、响应快、本地优先的桌面小工具：用户导入音频或视频文件，选择本地语音识别模型，得到忠实保留原语言的转写文本，并导出 TXT 或 JSON。桌面 GUI、CLI 和 MCP 共享同一套任务核心，让人和 AI Agent 都能提交、观察、取消、读取本地转写任务。

目标平台为 macOS 与 Windows。坚持“一次设计、统一信息架构和主要交互”，同时遵循 Apple HIG 与 Windows Fluent/平台习惯；用系统标题栏、文件选择器、快捷键、深浅色和辅助功能，不为了两端像素一致而重造系统外壳。

## 2. 已确认的用户决策（不可擅自改动）

- 主产品是**音视频文件转写工具**，不是语音输入法或常驻录音器。
- 不做实时麦克风听写；系统音频字幕/通话字幕只作为将来另行讨论的方向，不属于 V1。
- 本地推理是第一版核心；用户不希望默认走云端。转写时原始音视频不得上传。模型下载是独立的显式操作，模型已安装后转写应能断网运行。
- 同时面向普通用户与 AI Agent；桌面端、CLI、MCP 共用任务/模型/结果核心，不做两套互不相干的实现。
- 目标系统是 macOS + Windows；必须分别实机/目标平台验证，不能以一端构建成功推断另一端可用。
- 软件本体尽可能低占用、交互 responsive；保持小工具气质，不做大而全工作站或复杂常驻服务。
- V1 导出格式只保留 TXT 和 JSON。JSON 可承载结构化元信息及可选分段时间戳；不把 SRT/VTT/PDF/DOCX 增加为 V1 导出格式。
- 不做 AI 总结、翻译、笔记生成，也不把产品扩展成通用 AI 平台。
- UI 只设计一套。具体布局/视觉尚未定稿；可先做功能性临时界面供验证，但不得当作最终 UI。
- 产品名未定，使用英文占位目录名 `VoiceToTextApp`，不得把「声页」等建议升级为正式决策。

## 4. 明确不做（V1 非目标）

- 麦克风常驻、实时听写、语音键盘、系统级音频捕获。
- 云端 ASR/API 或默认网络回传；云端模型不作为“本地优先”的替代实现。
- 自动翻译、摘要、LLM 文本整理、课堂笔记/Anki 生成。
- 复杂字幕编辑器、剪辑工作站、多个文档导出格式。
- 公网/局域网 MCP 服务、远程控制面或任意文件浏览/读取能力。
- V1 开放用户安装任意第三方模型脚本；只集成经过审查的内置后端。

## 5. 功能需求

### 5.1 桌面工作流

- 提供系统文件选择器与拖放入口；接受格式清单须由所用媒体探测/解码链路实测后公布，不能仅按扩展名推断支持。
- 选择本地模型、自动识别语言（能力需按模型声明）；保留原语言，不擅自翻译。
- 展示任务状态：待处理、排队、运行、完成、失败、取消；只有后端给出可信数值时才展示百分比，否则显示阶段/已处理时长等诚实状态。
- 完成后在同一工作区查看纯文本预览、复制，并导出 TXT/JSON；导出失败必须可读且不得丢失任务结果。
- 多文件队列、历史、模型下载/卸载、取消与错误恢复是候选功能；通过里程碑逐项验收。
- 保持源媒体只读；失败/取消时不删除、不覆盖用户输入文件。

### 5.2 统一结果结构

建立版本化 JSON 结构，至少包含：schema/version、任务 ID、输入文件名（避免默认写入绝对路径）、模型 ID/版本、推理引擎版本、识别语言（未知可空）、媒体时长（未知可空）、完整文本、可选分段列表。每个分段若可用，记录文本与起止时间；模型不提供可靠时间戳时必须明确为空/不支持，不能伪造。JSON 导出应稳定、UTF-8、可机读；TXT 仅导出完整可读文本。

在实现前写 schema 示例和兼容策略测试；未来 schema 变更须增加版本号并覆盖旧数据读取策略。

### 5.3 CLI

CLI 与 GUI/MCP 共用应用层接口，不另写转写规则。至少提供模型列举、文件提交、任务状态、结果读取和取消的能力。命令的参数、退出码、stdout/stderr 语义须文档化；stdout 保留机器可读输出时，诊断写 stderr。

### 5.4 MCP

首版候选五个本地工具：

1. `list_models`：列出已安装/可用模型及能力，不宣称未验证的兼容性。
2. `transcribe_file`：提交转写任务，快速返回稳定 `job_id` 与初始状态，不因长文件占住一次 MCP 调用。
3. `get_job_status`：查询状态、可核验进度与错误摘要。
4. `get_job_result`：默认返回小型元数据/预览和本机结果位置；仅在 Agent 明确请求时返回完整文本，避免大结果默认灌入上下文。
5. `cancel_job`：取消仍可取消的任务，明确报告已完成/不可取消状态。

MCP 仅使用本地 stdio；不监听任何 TCP/HTTP 端口，不允许工具绕过任务核心读取任意路径。V1 输入授权契约为服务启动时显式传入可读目录（可重复指定 `--allow-root`）：输入必须是绝对路径，canonical path 必须位于某个授权根目录内；未配置授权根时 `transcribe_file` fail closed。不得提供任意输出路径、shell 执行或任意文件浏览能力。工具输入需验证路径、格式和模型 ID；错误信息不泄露凭据或本机不必要路径。

### 5.5 隐私与安全

- 音视频只在本机处理；网络只用于用户主动触发的软件/模型更新或模型下载，不隐式上传源文件。
- MCP 工具与 CLI 不具备任意命令执行能力；不得把 shell command 拼接成模型参数。
- 模型下载校验来源、长度/哈希与中断恢复；来源和哈希策略需在模型目录确定后冻结。
- 真实媒体、模型权重、转写文本、SQLite 用户历史、密钥和个人路径均不进入 Git。
- 失败与日志只记录必要诊断，不记录完整私人转写默认内容。

## 6. 候选技术架构与决策门

### 6.1 候选结构

- Desktop（当前已接受路线）：Tauri 2 + Svelte 单一桌面 UI；macOS 优先开发。优先系统标题栏与文件对话框，并实测主题/快捷键/无障碍；Windows 端须单独实机或 CI 验收。最终视觉设计仍待 Timmy 讨论定稿。
- Core：Rust 应用层/领域层，负责模型目录、输入验证、任务状态、取消、结果 schema、持久化与导出。
- Inference：独立 runner 进程候选，以故障隔离并在任务后释放模型内存；共享库/static 方案也可作为对照，须以实测决定。
- Backends：先验证 sherpa-onnx 官方 Rust crate（其仓库包含 Qwen3-ASR Rust 示例）；不满足门槛时用 whisper.cpp 评估专用适配。
- Media：FFmpeg 用于容器/音轨处理的候选；确定是否随应用分发、静态/动态链接及许可证义务后才选实现。
- Persistence：SQLite 是候选，保存任务和结果元数据；原始媒体仍留在用户原路径。
- Entry points：GUI、CLI、MCP 通过一个共享服务契约提交/观察任务。

### 6.2 推理引擎验证门

在选定引擎前对每个候选模型完成：

- Mac Apple Silicon 本机构建/启动/识别；Windows x64 目标机实际构建/启动/识别。
- 用可合法测试、内容固定的短样本，分别验证中文、英文和中英混合；记录模型/权重哈希、参数、耗时、实时率/速度、峰值内存、CPU/GPU 信息及文本质量观察。
- 验证 10 分钟以上素材切段/时间戳连续性前，再决定长文件切片策略；目标长片验收另单独执行。
- 检查模型许可、推理库许可、嵌入依赖、静态/动态链接、安装包增量、启动与释放内存。
- sherpa-onnx 当前静态 Rust 设置可能在首次构建时下载平台原生库；原生库体积与构建时间必须测量，模型权重另计。官方 API 示例存在不等于模型质量/双端发版已通过。
- 若 Qwen/Whisper 的模型、语言、硬件加速、质量或分发体积不符合门槛，记录失败原因后再评估专用后端；不得无证据宣称“统一 ONNX 一定更快/更省”。

## 7. UI 与双平台 UX 约束

- 主窗口单一主工作流，首屏突出拖入/选择文件、模型与开始操作；任务过程尽量原位呈现，不用重侧栏或复杂后台布局。
- 建议保留少量辅助入口（历史、模型、设置）；历史可先评估抽屉/弹层，但 UI 定稿尚未由 Timmy 选择。
- 状态化界面：空、已选文件、排队/转写、完成、失败/取消；高阶选项按需展开。
- UI 采用一套共享内容设计；遵循 macOS 与 Windows 各自的键盘习惯、系统菜单/标题栏、文件选择、深浅色、键盘导航/无障碍、高 DPI 与窗口缩放。
- 视觉方向偏简约、克制、低饱和、弱边框、少动画、文本清晰。不要花哨渐变、常驻动态效果或夸张“AI”视觉。
- 功能完成前可先使用明确标注的临时界面；最终视觉由 Timmy 再讨论/定稿，不因技术验证阻塞而擅自定版。

## 8. 轻量化与性能验收

不要给未测量的“只有 X MB”或“只占 X MB”承诺。每次比较使用同一机器、同一构建模式、同一模型和相同素材，分开记录：

- 空闲 GUI 启动时间/常驻内存/CPU；无任务时不能加载模型。
- 启动/退出模型 runner 的延迟和内存回收情况。
- 未下载模型时安装包大小、引擎 native libraries 体积、每个模型下载大小及总磁盘占用。
- 同一短音频的转写耗时、峰值内存、CPU/GPU 路径、识别结果质量；断网重跑已安装模型。
- 多任务/长文件/取消/崩溃重启时 UI 响应与数据恢复。

在开始最终性能验收前，根据首个原型读数与 Timmy 商定可量化门槛；门槛未定前只能报告基线实测，不可自行宣布达标。

## 9. 测试与发布验收

### 9.1 自动化测试

- 对核心结果 schema、TXT/JSON 导出、路径验证、任务状态迁移、取消、错误映射、数据库恢复与版本升级做单元/集成测试。
- 每个行为先写失败测试并验证失败原因，再实现；不以 mocks 代替核心实际逻辑。
- 引擎测试分开标明“mock/fixture 测试”与真实模型端到端测试。
- 结果 JSON 经标准解析器回读，TXT/JSON 文件写后重新读取、核对字段/编码/内容。

### 9.2 macOS 与 Windows 分别验收

两平台均需实际构建发行配置并验证：安装/启动/退出、文件选择、拖放、深浅色、窗口缩放、快捷键、任务取消、错误提示、模型下载中断/恢复、结果文件写入、MCP stdio 与 CLI。Windows 测试必须来自可识别的 Windows 机器/CI；不将 Mac 交叉编译成功当作 Windows 运行验证。签名/公证如未配置须标为发行阻塞，不伪称发布包已可公开分发。

### 9.3 真实场景验收

- 中文、英文、中英混合；自动语言与明确语言的差异如实呈现，原语言保留。
- 音频、视频实际解码；源文件修改时间/大小和内容保持不变。
- 长音视频需单列验收，检查分段拼接无漏字/重字与时间戳错位；模型不支持精确时间戳时明确限制。
- 模型崩溃、磁盘空间不足、网络下载中断、应用重启、用户取消时结果状态与可恢复部分正确。
- Agent 在 GUI 未打开时通过 MCP 提交、轮询、读取结果和取消；默认返回足够摘要，不自动返回超长全文。
- 完全断网后，使用已安装模型成功完成本地转写；确认无音视频上传。

## 10. 分阶段实施顺序

1. **需求/架构冻结前技术验证**：审核 sherpa-onnx 官方 Rust API 与 Vibe 工程结构；建立一条可重复的 Mac 短音频本地识别垂直路径，记录 Windows 阻塞、许可、模型权重与 native 包体事实。
2. **转写核心**：以测试驱动实现输入校验、统一结果结构、TXT/JSON 导出及单任务真实后端；用户媒体数据不进仓库。
3. **模型与任务层**：模型清单/下载验证/本地位置、任务状态/取消、持久化/恢复；每个平台逐项真实验收。
4. **CLI + MCP**：同一核心接口；MCP stdio 五工具和路径边界；CLI/MCP 不依赖 GUI 存活。
5. **桌面临时 UI**：Tauri 单窗口接入同一核心，做文件选择、状态和结果显示，验证平台行为；保留 provisional 标记。
6. **UI 定稿**：与 Timmy 讨论方案后再落实最终统一 UI；基于 Apple HIG/Windows Fluent 做少量平台适配并并行验收。
7. **双端打包/性能/发布**：在 Mac 和 Windows 分别实际构建、安装、截图/操作和性能测量；审查 FFmpeg/ONNX/模型许可、签名、公证和分发材料。

每个里程碑更新 `PROJECT_STATUS.md`：列出真实产物、命令、输出/截图或测试证据、未达项、下一门槛。不得把计划或可编译 stub 写成已完成。

## 11. 剩余验收门槛

- 在下载模型权重前，先审查精确模型版本、官方来源、许可、语言/平台矩阵、文件大小和校验计划，并取得 Timmy 对该下载的明确同意。
- 用合法、固定的短样本分别验证中文、英文和中英混合；核对真实文本、JSON/TXT、源文件只读、模型兼容性、耗时/内存与断网运行。无模型时不得伪造转写结果。
- 真实验证 GUI 启动的任务可由 MCP 观察、取消并读取结果；GUI 关闭后的任务生命周期也需单独确认。
- 在 Windows 主机或明确标识的 Windows CI 上实际构建并测试；Mac 构建不能代替 Windows 验收。
- 公开分发前审查 native/model/FFmpeg 许可、包体、签名、公证和安装器；未过门槛时标注为未发布。
- 每个阶段将实测结果、命令、未达项和下一门槛写入 `PROJECT_STATUS.md`；不要把可编译或协议握手误写为真实 ASR 完成。
