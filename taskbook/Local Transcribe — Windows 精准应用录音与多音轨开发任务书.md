## 1. 产品目标（必须实现的用户体验）

Local Transcribe 目前支持导入音视频文件并使用本地/局域网计算节点转写。现在要在 **Windows 客户端**内增设一个类似 Piezo / Audio Hijack 的轻量录音工作流：

- 用户点击「新建录音」，能够选择录音来源：**某个具体 Windows 应用程序的播放音频**，以及一个或多个允许的**麦克风输入源**（本阶段至少支持一个麦克风）。
- **只捕获被选中的应用的音频**。例如只选「腾讯会议」时，用户同时在 Spotify、浏览器等其他应用播放音乐，**未选中的应用音频不得混入目标应用音轨**。
- 用户勾选「腾讯会议」与「麦克风」时，生成**两个独立音轨**，各自保有音源身份、时间基准、时长与状态；**不是**先把两种声音混成一条不可拆分的录音。
- 显示每个音轨的实时输入电平、录制时长、录制状态；支持开始、停止，并尽可能支持安全暂停与继续（见分阶段准则）。
- 停止录音后，录音会话被保存到本机历史或录音管理入口；用户可以直接选择「转写」，**无需手动先导出文件、再重新导入**。
- 可以先按每条音轨分别转写并保存结果；统一合并视图须依赖可信时间戳，不能简单按文本顺序拼接造成错乱。
- 转写继续复用现有 Local Transcribe 队列、模型管理、结果页、TXT/JSON 导出、本地或 LAN Compute 计算目标。**不得另做第二套 ASR 引擎。**
- 录音默认不上传互联网服务；联网只用于用户既有明确选择的局域网远程转写和合法的软件依赖/项目开发工作。

### 非目标 / 明确不要做

- 不开发虚拟声卡驱动、全局声音劫持驱动或系统级音频注入驱动。
- 不使用普通扬声器全系统 loopback 伪装成单应用录音。
- 不做与 macOS 录音模块重复竞争的实现。
- 不强行实现自动说话人识别、AI 摘要、实时字幕、电话录音绕过或隐蔽录音。
- 不把所有正在运行的应用音频默认录下来；必须由用户主动选择来源并主动开始录制。
- 不破坏既有文件导入工作流、模型导入、历史、CLI/MCP、后台队列和 LAN 节点功能。

## 2. 关键技术路线（优先使用 Windows 官方 API）

### 2.1 精准捕获指定应用音频：Windows Application Loopback

优先基于微软官方 **Application Loopback Audio Capture** 方案：

- `ActivateAudioInterfaceAsync`
- `AUDIOCLIENT_ACTIVATION_PARAMS`
- `AUDIOCLIENT_ACTIVATION_TYPE_PROCESS_LOOPBACK`
- `AUDIOCLIENT_PROCESS_LOOPBACK_PARAMS`
- `PROCESS_LOOPBACK_MODE_INCLUDE_TARGET_PROCESS_TREE`

通过所选目标应用的**进程 ID / 进程树**限制采集范围，其他进程音频应被排除。该能力不需要依赖选定扬声器端点进行传统系统混音抓取。微软官方文档列出的最低版本为 **Windows 10 build 20348**；必须实测目标 Windows 版本、SDK 和音频环境，必要时在 UI 明确提示不支持。

**绝不能**将 `IAudioClient` 对扬声器终端的普通 `AUDCLNT_STREAMFLAGS_LOOPBACK`（系统混音）当作单应用隔离方案。普通 WASAPI Loopback 可作为**明确标注的全系统声音录制模式**的后续备选，但不属于这份任务的必达单应用验收路径。

参考资料：
- 微软官方示例：https://learn.microsoft.com/en-us/samples/microsoft/windows-classic-samples/applicationloopbackaudio-sample/
- 进程 Loopback 参数：https://learn.microsoft.com/en-us/windows/win32/api/audioclientactivationparams/ns-audioclientactivationparams-audioclient_process_loopback_params
- 传统系统混音 Loopback 的区别：https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording

### 2.2 麦克风采集

使用 Windows 标准音频输入能力（WASAPI capture 或经评估的成熟跨平台输入抽象，例如 cpal；**不能为了库方便牺牲稳定性**）。枚举已授权输入设备，能够选择默认或指定麦克风。处理设备被占用、权限禁用、热插拔、静音及输入格式变化。

### 2.3 Rust / Windows 原生桥接策略

维持 Rust + Tauri 共享核心。Windows 特有的 COM/Win32 Core Audio 逻辑可通过 Rust `windows` crate 或一层极薄的 C++/WinRT 桥接实现；选择以**实际可稳定编译运行**、容易维护、可控制资源释放为准。不可为了纯 Rust 教条化而拖延。

正确初始化 COM/apartment，按官方异步激活与回调规则处理音频客户生命周期；采集 callback 线程不得被磁盘、UI、网络操作阻塞。稳定处理 PCM packet、silence flags、format conversion 和停止/错误状态。

### 2.4 应用枚举与进程映射

- 枚举**当前正在运行且可选择的 Windows 应用**；展示友好名称、图标及必要的来源区分。
- 真实抓取需映射到可捕获的目标进程树，而不仅凭窗口标题或 `exe` 字符串臆断。
- 对多进程会议软件（腾讯会议、Teams、Zoom 等）验证实际渲染进程、子进程关系及程序更新引起的变化。
- 一个程序存在多个候选进程时提供清晰选择/识别，不要假定所有相同名称进程天然属于一个可覆盖的捕获范围。
- 捕获应用关闭或进程重启时，提示源已离线/重启；不可悄悄把音频范围扩大到全系统。
- DRM、受保护流、独占驱动及特殊渲染路径可能无法捕获；明示实际局限，不提供绕过机制。

## 3. 多音轨存储：不要只做两个声道的假多音轨

### 3.1 会话数据模型

建议创建 `RecordingSession` / `RecordingTrack` 两层数据结构，例如：

```text
RecordingSession
  session_id
  started_at / stopped_at
  duration / state / failure_reason
  tracks[]
  transcript_job_ids[]
  source_timeline / timing_reference

RecordingTrack
  track_id
  source_kind: application | microphone
  display_name / stable_source_identity / process_id_if_applicable
  sample_rate / channels / encoding
  start_offset / frame_position / timestamps
  file_path / sample_count / status
```

- 每个音源独立采集/写入；至少两路同时录音，架构允许扩展更多来源。
- 允许保留与源一致的声道数；录音过程中不自动合并音轨。
- 确保全会话统一单调时间基准，记录各音轨启动延迟与数据时钟差。
- 录音结果**优先采用每音轨独立的 WAV（必要时 RF64/分段文件）+ 一个会话 JSON 清单**，确保开发初期有可恢复、可调试且不会依赖复杂容器的实现；若已有成熟 MKV 多轨方案并通过真实验收，可作为后续封装/导出选项，不得为了容器格式损害录音可靠性。
- 长时间录音不得整段常驻内存；必须流式写盘、合理缓冲、定期更新持久化元数据并安全 flush。
- 注意常规 RIFF WAV 的约 4 GiB 边界，长录音采用分片、RF64 或经验证的大文件容器策略。

### 3.2 音频同步与异常恢复

- 采集线程共用可靠的单调时间轴；记录 source timestamp、样本计数和偏移。
- 两设备时钟不同步时，处理漂移而不是仅在开头人为填一次静音；需要时采用可验证的重采样/对齐策略。
- 同时说话时各轨可存在时间重叠，文本合并应按时间而不是按照文件完成时间排序。
- 麦克风可能物理拾取扬声器里的会议声音：这是**物理串音**，与指定应用捕获过滤的逻辑隔离不同。清晰说明使用耳机可以降低串音；不承诺凭空实现完全回声消除。
- 设备断开/被静音/源程序退出：单独标记该轨状态，尽量继续保存其他轨，不应无故丢失整场录音。
- 停止或异常退出后仍可恢复已完整落盘的录音片段；不把损坏的半成品标成“录制成功”。

## 4. Windows UI 交互与现有设计系统融合

保持已经确定的 **Local Transcribe 原生感 + 现代极简**视觉规范，不另做“Windows 管理后台”风格。录音入口可在「转写」页面的次要操作区域或轻量的录音工作区中出现，**不要突然增加第三栏或大型音频混音台**。

### 4.1 新建录音

- 显示录音会话名称（可默认时间命名）、声源选择列表。
- 声源类型：**应用音频** 与 **麦克风**，各来源可独立勾选；未选中来源不应被采集。
- 应用来源展示 App 名称/图标/当前运行状态；可搜索，能够刷新列表。
- 麦克风来源展示设备名称、权限/可用性状态；能预览输入电平。
- 开始按钮在至少选择一个**有效来源**后可用。
- 首次使用或系统权限限制时，提供简短可操作的指引；不要求安装虚拟音频驱动。
- 用户录制前应看到明显的录音预告/范围，录制后始终显示清晰的红色录制指示和累计时长。

### 4.2 正在录制

- 按音轨展示独立的输入电平、状态、静音/无音频警告、当前文件。
- 可「停止」；暂停/恢复若可安全完成则交付，否则拆成第二阶段，不能假装实现。
- 能可靠识别“目标应用没有输出声音”与“目标应用采集失败”；无音量不总是失败。
- 切换到历史、模型或设置页面不得终止录制。
- 不应在普通窗口关闭时隐式丢掉录音；沿用既有应用退出/后台规则并区分录音与计算节点。
- 明确显示剩余磁盘不足等真正影响录制的问题。

### 4.3 录制结束与转写

- 停止并完成文件保存后，显示录音会话详情（录音时长、轨道及来源、各轨文件状态）。
- 按音轨单独试听（如项目已有播放器）/导出；V1 必须能从录音直接创建转写任务，不要求先导出再导入。
- 支持「分别转写」至少两个轨道；继续复用既有模型选择、队列、Local/LAN 执行目标和历史结果系统。
- 遵循既有只读阅读式结果页：稳定文本、可选中和复制、TXT / JSON 导出。
- 如显示合并结果，必须保留音轨归属与实际可得的时间信息，不做无依据的说话人识别。

## 5. 后端接口与集成约束

- Windows 新增 capture backend 接口，供共享录音会话管理器调用。建议 `list_sources`, `start_session`, `stop_session`, `pause/resume (if supported)`, `get_meters`, `get_session`, `enqueue_transcription` 等能力。
- 跨平台共享类型应独立于 Windows 专有类型，不把 Win32 COM 类型泄露给 Tauri 前端或 macOS 后端。
- 采集线程、磁盘写入线程、UI 事件推送解耦；音量电平低频更新即可，不需要每个音频包都触发前端渲染。
- 与统一 Job Manager 集成：录音本身和 ASR 转写是**不同的任务类型/阶段**。录音期间可让其他转写任务运行，除非实测资源冲突；不能将录音错误当成 ASR 错误。
- Windows 录音后生成的媒体文件应能正常交给本地 ASR，也能在用户选择 LAN 计算节点后进入远程上传流程；**录音期间本身不必流式上传**。
- CLI/MCP 既有转写接口保持兼容；新增录音控制接口可按当前项目边界决定是否纳入第一批，但不能改变原接口语义。
- 记录必要、脱敏、可诊断的日志；不在日志中写入会议录音内容、敏感路径、令牌。
- 依赖与许可证审查，清晰标注官方系统 API、第三方库和发布二进制所需运行库。

## 6. 必须执行的真实 Windows 验收测试

**只在真实 Windows 系统运行/录制/监听过的项目，才可以标为通过。** 对腾讯会议若测试环境没有可用会议账号/对端人员，可用真实会议环境测试；暂不可测须明确标注，使用可控模拟应用做替代隔离测试，不能把替代测试说成腾讯会议实测。

| # | 测试 | 合格条件 |
|---|---|---|
| T01 | Windows 兼容性 | 判断 OS build 是否支持 Application Loopback；不支持时给出准确提示 |
| T02 | 指定应用隔离 | 目标应用播放音频，同时 Spotify/浏览器播放另一段可辨识音乐；目标轨中不得出现未选中应用音频 |
| T03 | 麦克风独立 | 同时讲话并录目标应用；两条音轨分别保存，可单独播放、检查 |
| T04 | 排除麦克风 | 只选择应用时，麦克风声音不得直接作为系统采集源混入（物理拾音情形另行区分） |
| T05 | 腾讯会议真实测试 | 确认音频输出进程范围与捕获效果，检查多进程及版本变化行为 |
| T06 | 多轨对齐 | 两个音轨的事件顺序、时长和同步偏差处于可解释的测试范围；公布测量条件与数据 |
| T07 | 长时间录音 | 至少一次 30–60 分钟持续录音，监测内存、文件增长、录音丢包与漂移 |
| T08 | 应用与设备状态变化 | 目标 APP 关闭/重启、麦克风拔插，UI 明确状态且已录数据可恢复 |
| T09 | 录制停止 | 停止后音频句柄释放，文件正常封口，重复开始/停止不崩溃 |
| T10 | 文件转写联动 | 停止录制后无需手动导出即可分别转写所选音轨 |
| T11 | Local / LAN | 已有 LAN 功能若可用，则检查录音结果能提交远程计算，并正确保持轨道/任务身份 |
| T12 | 资源与故障 | 磁盘空间不足、捕获启动失败、权限缺失、设备忙、异常退出时不伪报成功 |
| T13 | 安装器 | 在干净 Windows 环境安装 Early Beta 包，打开即可完成至少单应用+麦克风录音 |
| T14 | 回归 | 文件导入、模型切换、转写、历史、导出、LAN、CLI/MCP 现有能力不退化 |

**隔离测试特别说明**：应当使用两段内容可区分的测试音频，并分析目标录音输出，不能仅凭 UI 展示两个来源或两条电平条就宣称“精准捕获成功”。若腾讯会议实际音频由非子进程输出，需如实定位问题、研究能否安全精确捕获它的渲染进程；不得自动扩大到全系统采集范围以掩盖失败。

## 7. 分阶段实施与提交标准

### Phase A — 审计与可行性原型（Windows 客户端基线完成之后）

- 审查仓库、Windows 构建/部署方式和 macOS 录音模块共享契约。
- 记录系统版本、可用 Windows SDK、依赖/构建环境。
- 在真实 Windows 用微软官方示例或最小原型完成**指定应用捕获**；同时播放第二应用音频并检验隔离。
- 用真实麦克风同时采集并输出两条独立音频文件。
- 在 `docs/windows-recording-architecture.md` 保存结论、限制、参考 API 和测试证据。

**闸门**：若单应用精准隔离原型无法成立，不得把系统混音方案当成达标实现，先按无人值守规则排障；达停止条件后报告未解决阻塞并转做无依赖工作。

### Phase B — 可靠多音轨录音核心

- 抽象 Windows capture source、录音会话与轨道状态机。

## 8. 无人值守执行授权与排障额度

用户在睡觉期间可能不会回复，Agent 应按以下原则执行：

1. **不因小问题停工**：自行安装必要的 Windows SDK、C++ Build Tools、Rust 目标平台、项目依赖及文档明确必需的音频库；解决 PATH、版本冲突、包管理器、环境变量、构建脚本、系统依赖等常规问题。
2. 安装依赖只使用合法可信来源；保存依赖版本和必要许可信息，避免引入无法再现的系统修改。不要重置系统、格式化磁盘、关闭安全防护、绕过管理员权限或破坏用户现有软件。
3. 可以自主评估并选择技术方案，记录关键取舍，但不需要等待用户作答。
4. 对**同一独立阻塞问题**，上限为 **20 次有实质区别、可复盘的修复尝试**；若已评估约 **10 条真正不同的可行路线**仍无法解决，也应停止围绕该问题重复尝试。不得机械地重复同一命令凑次数；每次尝试记录假设、操作、输出与结果。
5. 达到上述停止条件后，不得对失败问题无限循环；保留日志、复现步骤和下一步建议，继续推进其他独立可完成任务。不要谎称已验收。
6. 如需 Home Assistant 唤醒 Windows 电脑，必须确认实体身份和状态；不可猜测开关或操作无关设备。使用现有合法访问方式；无权限无法建立访问时如实记下，不得绕过认证。
7. 与 macOS Agent 并行开发时优先在独立分支/工作树工作；禁止强制推送、清空他人未提交修改、覆盖进行中的代码；合并前运行必要测试。
8. 可以自主提交与推送经验证的代码，但公开 GitHub 之前遵守**已授权仓库范围**及敏感信息/历史扫描、许可证核查；禁止意外公开密钥、凭据、私人会议录音、真实测试音频、Home Assistant 配置或用户敏感路径。
9. 测试录音只使用自有或获得许可的内容；录制界面必须有清晰可见的录制状态，必要时提示参会者知情和适用法律要求。
10. 不要为避免小阻塞而削弱**核心验收标准**，尤其是不能用全系统音频录制顶替指定应用隔离捕获。
