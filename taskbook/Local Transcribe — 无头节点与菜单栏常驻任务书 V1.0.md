## 1. 用户已决定、不得重新讨论的边界

1. **不加鉴权、不加令牌、不加配对流程。** 用户的信任模型是「私有局域网 + 用户主动打开共享」。禁止为其增加任何形式的认证、证书或登录。
2. **但不得削弱已有防线。** 必须把 `LanScope`（只接受同私有子网对端）保留并扩展到无头节点路径；`--listen` 必须是私有 IPv4，不得默认 `0.0.0.0`。这是「不加鉴权」的替代条件，不是可选项。
   - 附带说明（**有意行为，不要"修复"**）：`LanScope::allows` 要求对端是私有 IPv4，因此**经 Tailscale（100.64/10）或其他非 RFC1918 地址访问节点会被拒绝**。这符合当前信任模型，本轮不放开；要支持 tailnet 应作为独立决策另做。
3. **拆进程是目标。** 验收时 GUI 不得再内嵌 `NodeServer`；「当一个节点」的实现只能留一份（无头节点）。
4. **本次不做开机自启。** 不安装 launchd / LaunchAgent / 计划任务，不写注册表自启项。
5. **不发布、不提交 Git、不建远端。** `beta.3` 发布仍处于暂停状态，本任务完成后也不要自行恢复。
6. **`crates/transcription-service` 只做 P3.5 的增量**（原「一行不动」的约束按用户决定放开）：新增可选的节点派发字段与远端执行分支。**本地路径的语义、状态机与锁顺序一律不得改动**，任何改动必须由测试覆盖。GUI 目前只用到它的 Ping（不承担转写），所以影响面是 CLI 与 MCP——但本地转写仍不得有任何退化。
7. **不改 `AGENTS.md`、不动 `GPT聊天记录/`。**

### 明确非目标

- 不做公网暴露、端口映射、UPnP、NAT 穿透、Tailscale 集成。
- 不做多节点负载均衡、任务分片、GPU 调度。
- 不做 Windows 托盘的真机验收（仅编译与资源包含）。
- 不重做局域网协议；`/api/v1` 与 `lan-compute` 的 23 个既有测试必须继续全绿。
- 不修复「两机 HTTP 超时」这个既有未验收项（见 `PROJECT_STATUS.md` 第 262–267 行），但也不得声称它已通。

## 2. 最终形态

两个二进制，共用同一套库（`lan-compute` + `transcription-core`）：

- `Local Transcribe.app` — 薄壳：界面 + 托盘 + 子进程监管。默认模式下不承担节点职责。
- `local-transcribe-node` — 常驻节点：HTTP API、任务存储、推理、mDNS/TCP 发现响应。随 App 一起打包（sidecar）。

用户可见行为：

- 设置项新增「关闭窗口后继续在后台共享」（默认跟随共享开关状态，共享未开启时该选项不可用）。
- 关闭窗口后：进程保留、菜单栏出现图标、Dock 图标按 P6 的策略处理；再次点击图标 → 主窗口回来且获得焦点。
- 菜单栏菜单项固定为：**打开主窗口** / 当前共享状态（只读） / **停止共享** / **退出**。
- 从 Finder 再次启动不会起第二个进程，只会把已有窗口带到前台。
- 菜单栏状态能反映：未共享 / 正在共享（显示地址与端口）/ 正在为某任务计算（显示任务或对端标识）/ 节点异常退出。
- **CLI 与 MCP 同样具备局域网派发**（P3.5）：命令行可用 `--node` 把任务交给节点，MCP 用 `list_nodes` + `nodeId` 选取；不给节点时一律走本机，结果与本地任务落在同一套历史与结果里。

### P2 · 补齐无头节点（本阶段可独立交付、独立实测）

在 `crates/lan-compute/src/bin/local-transcribe-node.rs` 上增量修改，不改协议：

1. **`--models-dir <目录>`**：用 `ModelLibrary::new(dir).list()` 扫描模型库，取其 `model` 作为 `Vec<LocalModel>`，走 `NodeServer::start_with_models`。保留 `--model-dir` 单模型参数以兼容既有用法；两者同时给出时 `--model-dir` 优先且不重复。
2. **默认模型排序**：`selected-model.json` 里选中的模型若在库中，排到首位（与 GUI 现有行为一致）。该文件路径**必须显式传入**（例如 `--selected-model <路径>`），**不允许从 `--data-dir` 反推上级目录**——`data-dir` 是 `<app data>/lan-host`，反推上级是脆弱耦合。读不到就按库顺序。
3. **`--netmask <掩码>` + 子网校验**：当 `--listen` 是私有 IPv4 时，必须同时提供掩码并走 `LanScope`（`start_on_lan_with_models` 等价路径）；缺掩码直接报错退出（退出码 2），错误文案说明为什么需要。仅 `127.0.0.1` 允许不带掩码（测试用）。
4. **`--listen` 默认值改掉**：不再默认 `0.0.0.0:7878`。改为必填或默认拒绝并打印用法（推荐：必填）。这是安全默认值修正，不是新机制。
5. **状态文件**：启动成功后原子写 `<data-dir>/lan-node.json`，内容至少含 `pid`、`name`、`address`、`port`、`version`、`started_at_unix_ms`、`served_models[]`；权限 0600；正常退出时删除；启动时若已存在且 pid 存活则拒绝启动（防重复）。
6. **`--parent-pid <pid>`（可选参数）**：给了就每 2 秒检查该 pid 是否存活，父进程消失则自杀退出。用于 GUI 崩溃时不留下孤儿节点。
   - Windows 上按 pid 探测存活需要额外 API；**优先用 Job Object**（`JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）让子进程随父进程退出，比轮询更可靠。两种做法都可以，但必须实测「父进程被 `kill -9` 后子进程会退出」，不得只写代码不验证。
7. **信号处理**：保留 Ctrl-C；收到后 `shutdown()` + `wait()`，删除状态文件。

**验收**：在本机 `127.0.0.1:7878` 起节点，用 `curl` 打通 `/api/v1/health`、`/api/v1/capabilities`、`/api/v1/models`；用 `LanClient` 提交一次真实 WAV 完成转写；状态文件内容与实际端口一致；`kill -9` 后重启能识别陈旧状态文件并恢复。
- **异常恢复不要重写**：`TaskStore` 在启动时已有把非终态任务标为 `failed`（`code: "interrupted"`）的逻辑（`crates/lan-compute/src/store.rs`）。本轮只需**验证它仍然生效**，不得删除或简化。否则客户端会永远等一个再也不会完成的任务。

### P3 · GUI 接管子进程（删掉进程内嵌）

1. 新增一个监管模块（建议 `apps/desktop/src-tauri/src/node_supervisor.rs`），职责只有四件：定位 sidecar 可执行文件、spawn（含参数拼装与父 pid）、`try_wait` 检测、`kill`/等待。
2. `lan_host.rs` 改为只做设置校验 + 调用监管模块；**删除**对 `NodeServer::start_on_lan_with_models` 的直接调用，GUI 进程内不再承载节点。
3. 保留 `HostState` 的对外形状与全部 Tauri 命令名（`lan_host_status` / `start_lan_host` / `stop_lan_host` / `lan_host_interfaces`），前端调用面不变。`HostStatus` 的语义改为「子进程当前状态」。
4. 模型列表不再由 GUI 传入，改为子进程自己扫描 `models/` + 读 `selected-model.json`。GUI 侧原来的 `ModelLibrary::list()` 拼装逻辑随之删除。
5. 节点数据目录继续用 `<app data dir>/lan-host`，保证既有已收任务仍可见。
6. 启动失败要把子进程的真实 stderr 前若干行透出到 UI（端口占用、缺模型、掩码不合法），不许只说「无法启动共享」。
7. **必须接管子进程输出（不做会静默卡死）**：子进程的 stdout/stderr 必须落地到日志文件，**不得留成无人读取的管道**。无人读取的管道缓冲区约 64 KB，写满后子进程会阻塞在 `write` 上——表现为「节点没反应」，既不崩溃也不报错，极难定位。
   - 推荐做法：直接用文件句柄作为子进程的 `stdout`/`stderr`（`Stdio::from(File)`），从根上不产生管道；若用管道，则必须有常驻读线程持续消费。
   - 日志路径用 `app.path().app_log_dir()`；单文件超过 5 MB 轮转，保留 1 份历史。
   - 日志里不得写入令牌、完整媒体路径清单以外的隐私内容（当前协议无令牌，保持现状即可）。

**验收**：开启共享 → `pgrep` 只看到 `local-transcribe-node` 在工作，GUI 进程不再监听 7878（`lsof -nP -iTCP:7878` 的持有者是子进程）；停止共享 → 子进程消失、状态文件删除；端口被占用时 UI 展示真实原因。

### P3.5 · CLI 与 MCP 的局域网派发（用户要求本轮完成；与托盘无关，可与 P4 并行）

前置：P2 的无头节点已能跑（用 `127.0.0.1` 即可验收，不需要另一台机器）。

**为什么必须做在 service 里，不要绕开**

CLI 和 MCP 都是 service 的客户端。若让它们各自直连节点，任务不会进入共享的 job store，`jobs list`、`get_job_result`、`export` 会全部对不上——等于造出第三套状态。所以派发发生在 service 的 worker 内。

**硬约束**

1. service 只做增量：`Request::Submit` 增加可选的节点目标（节点标识 + 可选远端模型）。**不传时行为与今天逐字节一致**；本地路径的语义、状态机、锁顺序一律不动。
2. 远端执行只复用 `lan-compute` 的 `LanClient`，**不得在 service 里重写 HTTP 协议**。
3. 结果必须落成同一份 `transcripts/<job_id>.json` 与 `JobStatus`，使 `get_job_result` / `export` / 历史列表完全无感。
4. **远端失败默认不回退本地**：状态就是 `failed`，带真实原因。只有显式 `--fallback-local` 才允许本地重跑；重跑沿用同一 job id，且只产生一条历史记录（与 GUI 现有行为一致）。
5. **取消必须传到节点**：POST `/cancel` 并停止轮询；不得只标记本地取消。
6. **节点来源**：读 GUI 保存的 `lan-settings.json` 中**已启用**的节点。不给 `--node` 时**一律走本机**，不继承 GUI 的 `prefer_lan`——脚本的默认行为不该被界面里的开关悄悄改变。
7. **MCP 不得接受任意地址**：工具参数只能传节点 id，且必须命中 `lan-settings.json` 中已存在的节点。**禁止** `host` / `port` / `url` 这类自由参数。这不是鉴权，是防止提示注入把文件发到任意内网地址。
8. **远端任务与本地任务共用同一个串行队列**：service 的 worker 一次只跑一个任务，远端任务**不得并行、不得插队**，排队顺序不变。一个长远端任务会让后面的本地任务等待——这是既有语义，不得为了「提升吞吐」改成并行。

**CLI 表面**

- `local-transcribe lan nodes` — 列出已保存节点与可达性（用 `LanClient::capabilities`，3 秒超时）
- `local-transcribe jobs add <文件> --node <id|name> [--lan-model <模型 id>] [--fallback-local]`
- 其余命令不变；输出仍为 JSON；退出码沿用 0 / 1 / 2 / 4

**MCP 表面**

- 新增只读工具 `list_nodes`：返回节点 id、名称、是否可达、当前模型
- `transcribe_file` 增加可选 `nodeId`；不传则本机
- 工具总数 8 → 9；同步更新 `docs/mcp.md` 的工具清单
- 仍为 stdio，**不新增任何监听端口**

**验收**

- 单机全链路（不依赖第二台机器）：`127.0.0.1` 起节点 → `jobs add --node` 提交真实 WAV → 轮询到 completed → `export` 写出真实文本 → `get_job_result` 与之一致
- MCP：`list_nodes` 能看到该节点；`transcribe_file` 带与不带 `nodeId` 各跑一次，结果分别来自节点与本机
- 远端失败：停掉节点后提交 → `failed` 且原因可读；加 `--fallback-local` 能本地完成且只有一条历史
- 取消：任务进行中 cancel → 节点侧任务也变为 cancelled
- 两机真机：若受既有链路问题阻塞，记录 blocked，不得声称已通

**测试（TDD）**

1. 派发决策：无节点参数时绝不走远端
2. 节点 id 不存在 / 已禁用 → 明确报错，不静默改本机
3. 远端失败默认不回退；显式回退才本地重跑且只一条历史
4. MCP 传未知 `nodeId` → 拒绝，**且不发起任何网络请求**
5. 远端结果写回后 `export` 与 `get_job_result` 一致

### P4 · 托盘 + 关窗不退出

### P4.1 · 模型空闲卸载档位（可配置，五档闭合）

**现状（基线核对时确认，不要凭记忆）**

- `crates/transcription-core/src/asr.rs` 中 `const IDLE_UNLOAD: Duration = from_secs(120)`，写死。
- `idle_unload_seconds()` 已经由 `lib.rs` 推给前端，`apps/desktop/src/lib/types.ts` 已有 `idleUnloadSeconds: number`，**但没有任何 Svelte 组件读取它** —— 界面从未提过这件事。
- 原始任务书 `taskbook/Local-Transcribe-V1.0-任务书.md` 第 131 行本就把它列为可设项（「模型空闲卸载时间（默认 2 分钟……）」）。本任务把这条补完。

**规则（用户已确认，不得更改）**

1. **五个闭合值，单位秒**：`20` / `120` / `600` / `1800` / `7200`。默认 `120`（维持现状）。
2. **永不提供「不卸载」**。任何 UI、配置文件、命令行都不得表达该语义；**不得用 `0` 或负数编码它**。长时间驻留只能通过 7200 表达。
3. **存储与传输一律用整数秒**；界面文字另做映射。不得把档位标签当作持久化格式。
4. **`--idle-unload <秒>` 必须命中闭集合**，否则拒绝启动（退出码 2 并打印允许值）。这是防止「永不卸载」被悄悄加回来的唯一闸门，**必须有测试**。
5. 设置文件读到缺失、非法或历史遗留值 → **回落到 120**，不得因此启动失败。
6. **单一来源**：设置存于既有设置文件；GUI 起节点时把值以 `--idle-unload` 传给子进程，node 不得自行读取设置文件。
7. **核心改造**：`const` 改为进程内一次性设定（`OnceLock<Duration>` 或 `AtomicU64`），必须在任何推理开始前完成；运行期不允许再改，避免并发语义含糊。保留 `idle_unload_seconds()` 作为读取入口。

**两份取值：界面与节点分开设，共用同一闭集合**

界面进程和节点子进程的最优值本来就不同：界面可能连着处理十几个文件，节点可能几小时才来一个任务。所以要分成两项，各自独立。

- 设置项两个：**「本机转写」** 与 **「局域网节点」**，各自从同一组五个值里选（20 / 120 / 600 / 1800 / 7200）。
- 默认值**两者都是 120**，不发明不对称的默认。
- 存储为两个独立字段（例如 `idle_unload_gui`、`idle_unload_node`），任一读到非法或缺失值只回落该项自己到 120，不得互相影响。
- GUI 启动子进程时把**节点那一项**用 `--idle-unload` 传下去；界面自己那一项在进程内设定。**两者不得串用。**
- 节点行在共享关闭时置灰，并说明「开启共享后可设」；不得隐藏到用户找不到。
- 设置项旁边给一句提示：长时间无人使用可设 20 秒，批量处理期间可设 10 分钟。

**必须一并修复的既有缺陷（TDD，先红后绿）**

现在 `last_used` **只在创建缓存时写入，命中复用时不刷新**，因此计时实际是「从加载起算」而不是「从最后一次使用起算」。

在 20 秒档位下这会变成用户可见的 bug：一个 30 秒的任务可能刚跑完就立刻触发卸载，用户会觉得「我刚用完它就卸了」。

要求：缓存命中时刷新、任务结束（成功 / 失败 / 取消）时也刷新；空闲计时从**最后一次使用结束**起算。

测试方式：不要真等 20 秒。抽一个内部接缝接收 `Duration`（以及可选的 tick 间隔），用毫秒级时长断言「任务结束后未达阈值不卸载、超过阈值卸载」。

**顺带确认一个既有行为（不要改坏，也不要放任）**

`RECOGNIZER_CACHE` 的 `MutexGuard` 目前在整个推理循环期间都被持有，因此同进程里任何读取缓存的调用都会被挡住，包括模型状态查询（界面绿点用的 `loaded_model_id()`）。现象不是崩溃，而是**转写期间绿点查询一直挂起，任务结束才返回**。

在改这个锁的时候要确认：这次查询不得被长时间阻塞。若确实阻塞，把 guard 的作用域收窄到「取到识别器引用为止」，或让状态查询走一份独立的原子量（例如记住当前模型的 id 与最后使用时间），**不得为此改成无锁共享识别器**——识别器本身不能被并发调用。

**UI**

- 设置页新增一项，五个可选项加一句人话解释，默认选中「平衡 · 2 分钟」。
- 「20 秒」档的文案必须说明代价：转完即退场，下一个文件要重新加载。
- **最终文案待 4.1 的 M1 数据出来后再定稿**；本阶段先把数值、校验、持久化做对。
- i18n 五种语言全部补齐；沿用已存在的 `idleUnloadSeconds` 通道，不要新增并行命令。

**验收**

- 切到 20 秒 → 真实转一个文件，结束后 20±5 秒内 `loaded_model_id()` 变空且 RSS 回落。
- 切到 7200 → 同样窗口内模型保持驻留。
- 设置文件手写 `999999` → 启动回落到 120，正常可用。
- `local-transcribe-node --idle-unload 999999` → 退出码 2，打印允许值。
- **两份取值互不影响**：把「本机转写」设 20 秒、「局域网节点」设 7200，分别验证——界面进程约 20 秒后释放模型，同时节点进程的模型保持驻留；反过来设一次也要成立。

### P4.2 · 后台形态的产品细节（用户已逐条确认，照做，不得重新设计）

**1. 共享状态跨启动保持**

- `lan-settings.json` 增加 `share_on_launch: bool`：开启 / 停止共享时写入，关闭共享写 `false`。
- 启动时若为 `true` 且上次的网卡与端口仍有效 → 自动启动子进程，托盘直接显示真实状态。

- 首次安装（无该字段）默认 `false`，与今天行为一致。

**2. 退出保护弹窗**

- 触发点：托盘「退出」、⌘Q、应用菜单退出。**关闭窗口不触发**（不中断）。
- 判定：`/api/v1/tasks` 中存在非终态任务时弹窗。
- 弹窗必须显示：任务数量、每个任务的文件名、当前阶段、进度（能拿到就给百分比，拿不到就写阶段名，不许编造数字）。
- 文案说明「退出会中断这些任务，对方需要重新提交」。
- 按钮：`取消`（默认）/ `仍要退出`。
- 无法连接节点、拿不到任务列表时**仍要弹窗**，文案改为「无法确认是否还有任务在进行」。

**3. 节点接收媒体的自动清理**

- **复用既有 retention 机制与既有 UI 模式**，不要新造第二套控件风格：新增独立设置项（`lan-host` 专用），三档 `off | age | size`，沿用既有选项集合（1/3/5/7/30 天；1/5/10 GiB），**默认 `off`**。
- 只清理 `lan-host` 下**处于终态**任务的媒体；非终态任务一律不碰。
- 节点当前没有「结果是否已被取回」的记录，因此**天数下限不得低于 1 天**，且默认关闭；这一限制写进设置项说明。
- 删除一律走既有 `move_to_trash`，禁止 `rm`。
- 清理时机：节点启动时、每次任务结束后（对齐 `apply_retention` 的既有调用点）。
- 局域网页显示 `lan-host` 当前占用与条目数。
- **Windows 注意**：`move_to_trash` 目前只有 macOS 实现（非 macOS 为占位）。若本轮未实现 Windows 回收站，则 Windows 上此开关必须**禁用并说明原因**，绝不允许退化成 `rm`。

**4. 路径规范与「数据位置」总览**

- **现状已正确，不要"顺手修正"**：`app_data_dir()` 用的是 `app.path().app_local_data_dir()`。macOS 得到 `~/Library/Application Support/com.timmy.voicetotextapp`，Windows 得到 `%LOCALAPPDATA%\com.timmy.voicetotextapp`。**不要改成 `app_data_dir()`**——Windows 上那是 Roaming，会把 GB 级模型放进漫游目录。必须在函数上写明这条注释。
- 新增日志目录：用 `app.path().app_log_dir()`（macOS `~/Library/Logs/com.timmy.voicetotextapp`，Windows `%LOCALAPPDATA%\com.timmy.voicetotextapp\logs`）。

## 4. 硬性验收标准

全部满足才算完成；缺一项就如实列出为未完成。

1. **两个二进制**：GUI 与 `local-transcribe-node` 均从安装路径可运行，版本号一致。
2. **单一实现**：GUI 进程内不再内嵌 `NodeServer`（代码可查）；「当一个节点」只有一份实现。
3. **后台常驻**：关窗后节点存活，另一台机器仍能发现并提交任务。
4. **真正的进程隔离**：关窗后 `lsof` 显示 7878 由子进程持有，不是 GUI 进程。
5. **二次启动**：连续启动两次只有一个 GUI 进程，第二次只唤起窗口。
6. **崩溃兜底**：`kill -9` 子进程后，托盘状态在 5 秒内变为「节点异常」，且可从托盘一键重启；带 `--parent-pid` 时，GUI 被 `kill -9` 后子进程在 5 秒内自行退出。
7. **真实内存数字（必须实测，不许估）**：分别记录并写进日志——
   - 节点空闲 RSS（`ps -o rss= -p <pid>`）
   - 节点计算中 RSS（跑一次真实 WAV 转写时）
   - GUI 关窗后 RSS
   - 三方对比本轮改动前后的差异
   - **另见 4.1 的重叠推理测量，三条数字不够，必须做 M1/M2/M3**
8. **安全默认值**：`--listen` 不再默认 `0.0.0.0`；非私有地址或子网外的对端被拒（用单元测试覆盖 `LanScope::allows` 的边界）。
9. **既有能力不退化**：`cargo test --workspace` 全绿；`lan-compute` 的 23 个测试一个不少；前端 `npm run check` / `npm run build` 零告警；`cargo clippy --all-targets -- -D warnings` 在 macOS 与 Windows 目标均清零（Windows 无法执行时标记 blocked）。
10. **两机验证**：macOS 两台机器（MBP 与 Air）之间发现 → 提交 → 完成 → 取回结果。若仍被既有 HTTP 超时问题阻塞，如实记录阻塞点，不得伪造成功。
    - **必须做一次绕开 GUI 的对照**：在终端直接跑 `local-transcribe-node`，用 `LanClient` 或 `curl` 从另一台机器请求。这一步与 GUI、WebView 无关，是把故障分层的关键。
    - 采集系统 ALF 日志证据，明确回答：是否卡在 macOS 的入站连接授权弹窗。
    - 结论必须落到「授权问题 / 协议问题 / 端口或防火墙问题」其中之一，并附证据。
    - 本项不要求修通，但**要求给出可据此行动的诊断**；只写「仍然不通」不算完成。
11. **后台形态（P4.2）四项**：共享状态跨启动恢复（网卡失效时不得静默降级）、退出保护弹窗（含文件名与真实进度）、`lan-host` 清理（默认关闭、只删终态、走废纸篓）、首次开启的知情同意——四项均在本机实测通过。
12. **路径与可见性**：设置页能列出并打开全部六个路径；`storage_summary` 已含 `lan-host` 与日志；确认 `app_data_dir()` 仍使用 `app_local_data_dir`（Windows 不得落到 Roaming）。
13. **托盘状态**：未共享 / 共享中 / 计算中 / 异常 四种情形与定义一致；health 失败不得显示成「共享中」；切换语言后托盘菜单重建并生效。
14. **子进程日志**：以文件句柄接管 stdout/stderr；由子进程写入 ≥ 2 MB 连续输出时**不阻塞、不卡死**；超 5 MB 轮转生效并保留 1 份历史；设置页能打开日志文件。
15. **两份卸载时长**：「本机转写」与「局域网节点」可在同一组五个值内分别设置、互不影响，且各自被对应进程实际采用（用一长一短实测验证）。
16. **CLI 局域网（P3.5）**：无 `--node` 时始终本机；`--node` 在 loopback 上跑通全链路；远端失败默认失败、`--fallback-local` 可回退且只留一条历史；取消能传到节点。
17. **MCP 局域网（P3.5）**：`list_nodes` 存在；`transcribe_file` 的 `nodeId` 只能取已保存节点，未知或已禁用节点被拒且不发起网络请求；工具总数 9，`docs/mcp.md` 已同步。

## 4.1 模型驻留与重叠推理（必须实测，不许推断）

### 背景：这不是假设，是代码事实

- `crates/transcription-core/src/asr.rs` 定义 `static RECOGNIZER_CACHE: std::sync::Mutex<Option<CachedRecognizer>>`，即**进程级、单槽位**缓存；常量 `IDLE_UNLOAD = 120 秒`，空闲后整槽释放；`loaded_model_id()` 报告当前真正驻留内存的模型。
- `crates/lan-compute/src/node.rs` 的 `run_task` 直接调用同一个 `transcribe_file_cancellable`，因此今天节点任务与 GUI 本地任务**共用同一个缓存槽**。
- 结论（今天的状态）：**不可能同时驻留两个模型**；当两边使用不同模型时会反复「卸载 → 重载」，表现为抖动，而不是内存翻倍。GUI 的「同一时刻只允许一个任务」只约束 GUI 自己的队列，不约束节点收到的任务，两者可以同时推理。
- 结论（拆进程之后）：每个进程各有一份缓存槽，**峰值内存可以真的翻倍**，但抖动消失。这是一次用内存换响应性的取舍，**必须用数字证明它值，或明确写出限制**。

这是本项目 `taskbook/Local-Transcribe-V1.0-任务书.md` 早已写明、但一直未被满足的设计约束（原文：「如果推理只存在于 Tauri 主进程……而且 MCP/CLI 可能重复加载」）。本任务把它从「隐患」变成「已知代价」，不允许继续含糊。

### 必须完成的三组测量

全部使用真实模型与仓库内真实音频，记录命令与原始输出。

**M1 · 拆进程之前的抖动基线（现在就做，无需改代码）**
用当前已安装版本即可：本机选模型 A 跑一段真实音频；再把节点收到的任务指定为模型 B，交替各跑两次。记录每次「切换」后的首个任务耗时与同模型连续两次的耗时差（差值即重载成本），以及切换前后的进程 RSS。**必须在 P3 删除内嵌路径之前完成，否则这组数据永久丢失。**

> 实现方式不依赖网络：若两机链路仍未通、或本机自访 LAN 地址仍 HTTP 超时，不要在网络上耗时间——改用**同进程集成测试**复现：在同一个测试进程内启动 `NodeServer`（模型 B）并对本机发起一次任务，同时用模型 A 跑一次 `transcribe_file_cancellable`。两次调用落在同一个 `RECOGNIZER_CACHE` 静态槽上，抖动的成因与真实场景完全相同，且与网络无关。两条路径（真实链路 / 同进程测试）任选其一，但必须说明选了哪条。

**M2 · 拆进程之后的重叠（P3 完成后）**
节点正在用模型 X 计算时，GUI 本地再发起模型 Y 的任务。记录：两个进程各自 RSS、合计 RSS、各自耗时、是否因争用而变慢或失败。

**M3 · 静息释放（两边都空闲 130 秒后）**
分别记录 GUI 与节点进程 RSS，验证 120 秒空闲卸载在每个进程内各自生效，而不是只在一个进程里生效。

### 必须给出的结论（写进日志 + README + PROJECT_STATUS）

1. 拆进程前后，峰值内存差多少（给具体 MB，标明模型）。
2. 拆进程前后，切换抖动是否消失（给具体秒数差）。
3. 一句话限制说明：共享期间若本机同时跑大模型，会占用双份模型内存。这句必须出现在用户能读到的地方，不允许只写在日志里。

### 约束

- 至少测两个量级不同的模型：「准确优先」组取 FireRedASR2（1.15 GB）、「速度优先」组取 Zipformer CTC small。
- 禁止用估算、理论值或「应该差不多」代替实测。
- 若 M2 显示合计 RSS 在 8 GB 机器上已接近不可用，必须在 UI 给出提示或提供一个「共享期间暂停本机任务」的可选互斥开关；**不得沉默**。
- 数字难看也要如实保留，不得因为不好看而删掉本节记录。
